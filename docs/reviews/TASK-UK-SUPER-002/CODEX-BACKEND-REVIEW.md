Antigravity reports that 2,079 rows were staged in local Supabase and its 12 integration tests passed. I inspected the migration, test, contract, proposal, and local draft. ## Release-blocking findings

1. **P0 — Anonymous calls may execute all four privileged RPCs.** `supabase/migrations/20261104000014_14_product_draft_staging.sql:106-133`, `:252-278`, `:360-391`, and `:522-548` declare `SECURITY DEFINER` functions. Each allows a null `auth.uid()` when `current_user` is `postgres` or `service_role`. Inside a security-definer function, `current_user` is the function owner, not the caller. The migration revokes direct table access but never revokes default `PUBLIC` function execution or grants these RPCs to limited roles. As written, a caller with no authenticated user can likely stage, resolve, publish, and read summary data for a known organization ID. Antigravity must check the actual local grants and test calls with an anon key, then fail closed on a null `auth.uid()` unless the caller's invoker role is explicitly and safely verified. Revoke `EXECUTE` on all four signatures from `PUBLIC` and `anon`; grant only the intended roles in the migration. RLS on the tables cannot compensate for a privileged RPC that bypasses it.
2. **P1 — Any active member can mutate catalog data.** The same four authorization blocks check active organization membership only. The [contract](../../integration/TASK-UK-SUPER-002-PRODUCT-IMPORT-CONTRACT.md) promises owner or `inventory_edit` authorization for staging. Add role/capability checks to each mutation RPC and tests for an active member without that capability. Keep summary read access aligned with its separately documented policy.
3. **P1 — Publishing bypasses anomaly review and can abort a batch.** `publish_product_drafts` at migration lines 394-405 only skips already-published rows. It does not require `resolved` status, cleared `review_flags`, valid prices, or a decision on missing barcode/category. Lines 455-480 then copy the values into products, replacing missing prices with zero. Staging prices are `NUMERIC(18,2)` while product prices are `NUMERIC(12,2)`; the documented source ID 114 wholesale value `8,901,058,905,113.00` fits staging but overflows the product column. Enforce publish eligibility and field bounds before insertion; return item-level errors without corrupting or aborting the rest of the requested batch. Test an unreviewed flagged row, source ID 114, and null price fields.
4. **P1 — Re-staging erases review work.** The upsert at migration lines 189-200 replaces corrected name, barcode, category, prices, and review flags for any draft except `published`, while preserving its `reviewed` or `resolved` status. Restrict source updates to untouched staged rows, or preserve human edits and their review state with an explicit version/conflict policy. Test a corrected draft followed by an identical or changed source retry.
5. **P1 — Integration test can delete hosted test-account data.** `tests/integration/product-draft-staging.test.ts:6-12` accepts `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from the environment without verifying localhost. Setup deletes *all* `products` and `product_drafts` for the `test` organization at lines 73-74. A run with hosted credentials could remove hosted data. Fail closed unless the URL is an approved loopback local endpoint, use a dedicated disposable local organization, and clean up only rows created by the test. This guard must run before any admin client, sign-in, or delete.

## Evidence and contract corrections

6. **P2 — Zero-stock test proves nothing as written.** At test lines 233-250, PostgREST queries `information_schema.tables`, ignores query errors, and treats null data as a zero-row success. Replace with a reliable local SQL/schema check, assert errors, and verify row counts if stock tables exist.
7. **P2 — Source ID range and reconciliation claim are wrong.** The local draft contains 2,079 unique IDs with minimum 6 and maximum 2211. The proposal states `1–2140` at lines 29 and 121. The test checks count and distinctness but does not compare the staged `(source_file, source_id)` set to the source manifest. Correct the proposal and test exact source identity, including per-file counts or hashes. The contract's staging price columns at lines 95-96 also say `NUMERIC(12,2)`, unlike the migration's `NUMERIC(18,2)`.
